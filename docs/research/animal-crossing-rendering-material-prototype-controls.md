# Animal Crossing rendering and material controls for the Grand Gallery

Research resolution for [Research Animal Crossing rendering, baking, and polygon treatment](https://github.com/Reid-Surmeier/risd-godot/issues/152), 2026-09-27. **Decision:** preserve the New Horizons human source mesh, skin, and UVs as the first character control; test restrained painted materials and spatial light response at the actual gallery size before reducing polygons or changing the final display pass. The existing gallery pipeline already covers much of the proposed display and static-room treatment. This report proposes a comparison, not an accepted character or a reconstruction of Nintendo's shader.

**Evidence labels:** **S** = primary source or repository code; **F** = inspected game frame; **P** = proposed prototype setting or pass criterion. The GameCube code below is a community decompilation and Dolphin is an emulator implementation, not Nintendo's authoring file or proof of a particular pixel in a captured video. None of the footage exposes exact mesh triangle counts, UV island boundaries, bake maps, light energies, or capture hardware.

## Current gallery control, inspected at `55e7c3b7`

| Stage | Current implementation | Material implication |
| --- | --- | --- |
| Room | [`bake/prepare.gd`](../../modules/shell/prototype/gallery_walk4/bake/prepare.gd) copies base UV/materials, gives static geometry unique UV2, and bakes two bounces with five fill omnis, painting spots, daylight, and probes. The static floor hint is 512×1024; other meshes unwrap at 0.12 m. The exported room is rendered without runtime lights. | Static illumination is already baked. Replacing a room texture requires regenerating the baked scene; adding a character UV map does not change the room bake. |
| Visitor | [`identity/build.py`](../../modules/shell/prototype/gallery_walk4/identity/build.py) authors the current 5,104-triangle visitor with ten solid-color material primitives and **no image textures**. Its KayKit motion/skin is a technical control, not a New Horizons source proof. |
| Sampling and finish | [`walk4.gd`](../../modules/shell/prototype/gallery_walk4/walk4.gd) uses 2× MSAA, linear viewport enlargement and width-based integer `stretch_shrink` around a nominal 480-pixel width. [`gamecube.gdshader`](../../modules/shell/prototype/gallery_walk4/gamecube.gdshader) does RGB6-style raster quantization, a half-strength vertical copy filter and bilinear reconstruction. Room materials use mipmapped anisotropic filtering; [`oak.gdshader`](../../modules/shell/prototype/gallery_walk4/oak.gdshader) widens the grain footprint and blends 60% texture. | A finish change would confound a material trial. Nominal `480×320` is not a guaranteed actual viewport size: record `_vp.size` on each capture. The half-strength copy filter is a project choice, not a known AC mode. |

The [visitor UV bake trial](gallery-visitor-uv-bake-trial.md) already proved a Blender → skinned GLB → Godot transfer with 512² albedo/AO maps, yet its placeholder shirt showed **no clear gain at the 720-pixel embedded viewer size**. The [light-response trial](gallery-light-response-trial.md) found no winner for a global probe-gain change. These are reasons to demand visible improvement from a specific material or shape, not to run a larger blind texture/bake pass.

## Small, measurable prototype

1. **Lock a source control.** Preserve the untouched New Horizons PlayerBody mesh and textures, with file hash, triangle count by visible part, UV sets, material/texture dimensions, skin joint count, and animation inventory. Capture front, profile, rear, idle, walk, stop, and turn. Record the same values for each derivative. The source's acquisition and permissions are tracked separately in the [character asset study](2026-09-27-character-asset-sources.md); a found model is not itself a licensed final gallery asset. **P pass:** GLB inspection finds the expected `POSITION`, `TEXCOORD_0`, `JOINTS_0`, `WEIGHTS_0`, skin, and texture references for each skinned visible primitive; no unexplained missing face/clothing map. These fields are defined by the [glTF 2.0 specification](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html).
2. **Run one material comparison on that same geometry.** A = untouched source albedo/materials; B = copied material with broad painted color/motif treatment on one visible garment or hat, with UV0 and face textures unchanged. Hold rig, scale, camera, bake, light probes, contact, viewport and final pass fixed. If B needs a distinct UV, make it only for that surface and export the texture coordinate selection explicitly; [Blender's bake rules](https://docs.blender.org/manual/en/4.3/render/cycles/baking.html) require an active target image and UV map. **P pass:** at the real 1080×1080 Square Stage and a 720-pixel embedded comparison, the edited region occupies at least 2 internal pixels across its smallest required motif, remains legible in front/profile/motion, and does not smear over face, seam, or eye. This 2-pixel threshold is a proposed visibility gate, not a Nintendo texture specification.
3. **Change polygons only after a contour failure is located.** Overlay A and B against one chosen Nintendo or owner frame at matched character pixel height, and capture front/profile/rear against the untouched source. Mark which silhouette arc or joint reads wrong; edit that part only. **P pass:** no disappearing hands/shoes, no visible joint tear through a full walk/turn cycle, and no new silhouette break wider than 2 internal pixels outside the deliberately changed region. Log triangles before/after and reject a reduction that saves geometry without improving a marked contour. The 2-pixel limit is a prototype review tolerance.
4. **Keep two lighting questions separate.** Room UV2/lightmap stays fixed for the character A/B. For the moving visitor, compare the current probe plus contact-card result with a single bounded alternative only if the matched captures show a specific failure. Record displayed luma from the *same* wall/floor material patches and visitor patch at warm and cool positions, plus shoe-to-floor gap/contact footprint in internal pixels. **P pass:** the visitor changes visibly with position, the cream/skin detail survives both locations, no double-dark halo appears, and the contact remains under the planted sole throughout movement. Static LightmapGI cannot bake a moving visitor's changing position; its dynamic probes provide indirect light, per [Godot's LightmapGI guide](https://docs.godotengine.org/en/4.7/tutorials/3d/global_illumination/using_lightmap_gi.html).
5. **Judge in motion and at output size.** Use the same browser export and camera path for A/B, including doorway, white room, warm gallery, quarter-turn, stop/reversal and painting approach. Record actual viewport dimensions, device-pixel ratio, frame times and transferred pack bytes, plus paired lossless captures and a short clip. Run `scripts/check-gallery.sh`, `scripts/check.sh`, and `git diff --check` on any implementing branch. Acceptance requires a blind still/motion comparison and the owner's visual judgment under the map's World Asset Gate; technical GLB validity alone is insufficient.

**Answer to the ticket:** source-backed GameCube evidence favors readable modeled silhouettes, broad textured color, several lighting paths and filtered low-resolution output. It does **not** establish that the game used universal unlit textures, universally baked character shading, nearest-neighbor textures, a single polygon count, or a recoverable exact shader from compressed footage. The next build should test one New Horizons-based asset treatment against the frozen gallery control; only a measured visible gap justifies geometry simplification, a character-specific light treatment, or a display change. Research spend: **$0**.
