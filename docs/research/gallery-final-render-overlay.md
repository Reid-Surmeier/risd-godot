## Primary hardware evidence

**V:** the GameCube decompilation's `emu64_init()` enables `GX_PF_RGBA6_Z24` and dithering. This supports six-bit color behavior for this renderer, not a five-bit PS1 effect. [Pinned Animal Crossing emu64 source](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/static/libforest/emu64/emu64.c#L573-L580)

**V:** Dolphin implements the Flipper 2×2 ordering as `((x ^ y) & 1) * 2 + (y & 1)` and subtracts the original eight-bit value shifted by six before adding this offset. Existing `_post()` already follows that arithmetic. This identifies a hardware operation, not proof that every Godot blend/color-space operation is equivalent. [Pinned Dolphin pixel shader generator](https://github.com/dolphin-emu/dolphin/blob/465c652da1dc0b3048089701a1885084821c9574/Source/Core/VideoCommon/PixelShaderGen.cpp#L1008-L1015)

**V:** Animal Crossing declares a 640×480 interlaced mode with display-copy coefficients `{8,8,10,12,10,8,8}`; progressive uses different coefficients. Normal mode selection depends on `video_progressive`, so a recording's mode cannot be inferred from its upload dimensions alone. [Pinned video mode source](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/static/jsyswrap.cpp#L130-L177)

**V:** Dolphin groups coefficients 0–1 into the preceding row, 2–4 into the current row, and 5–6 into the next row. The stated interlaced coefficients consequently produce weights **¼, ½, ¼**. [Pinned coefficient grouping](https://github.com/dolphin-emu/dolphin/blob/465c652da1dc0b3048089701a1885084821c9574/Source/Core/VideoCommon/TextureCacheBase.cpp#L1945-L1955) The display-copy shader applies this RGB filter after EFB format conversion, before optional gamma/YUV conversion; alpha is retained separately. This establishes why filtering the dithered result is preferable to dithering an already enlarged image. [Pinned display-copy shader](https://github.com/dolphin-emu/dolphin/blob/465c652da1dc0b3048089701a1885084821c9574/Source/Core/VideoCommon/TextureConversionShader.cpp#L107-L174)

## Actual local pipeline and gaps

This is the inspected route, in order:

1. [`walk4.gd`](../../modules/shell/prototype/gallery_walk4/walk4.gd) constructs lit LightmapGI room meshes and the character inside `_vp`, a `SubViewport`. `msaa_3d=MSAA_2X`. `LOW_RES=(480,320)` is a target, not a fixed 480×320 framebuffer: `stretch_shrink=round(view_width/480)` is an integer divisor of actual container dimensions. Only the width constant participates. Native viewport dimensions therefore change with the window and divisor thresholds. [Godot SubViewportContainer](https://docs.godotengine.org/en/stable/classes/class_subviewportcontainer.html)
2. `SubViewportContainer` linearly samples that viewport. Its attached `_post()` shader samples with `texture(TEXTURE, UV)`, then performs RGB6 reduction with a matrix addressed by native texel indices. **V:** quantization runs per output fragment, after the sampler's interpolation. **I:** this is not native RGB6 followed by enlargement; interpolated gradients can cross new thresholds inside one enlarged texel.
3. The result joins desktop/UI in the shell's `Desktop` viewport. [`crt_luminance.gdshader`](../../modules/shell/crt_luminance.gdshader) samples six desktop texels, applies gamma-aware reconstruction and channel offsets, then mask, scanline and grain. Gallery `quiet_rect` scales the last three contributions to 12%; it does not remove channel separation or reconstruction. [`demo.tscn`](../../modules/shell/demo.tscn) sets curvature 0.018. [`crt_display.gd`](../../modules/shell/crt_display.gd) maps mouse input through the same curvature.
4. Optional Squiggle layer 10 is off by default. Layer 11 [`haze_screen.gdshader`](../../modules/shell/haze_screen.gdshader) remains on by default: twelve offset samples, 1.6 output-pixel radius, 45% blend. It processes the gallery again and does not honor `quiet_rect`.

**V:** the existing finish is independent of `TIME`, but that alone does not prove stable movement. Texture minification, changing raster alignment and stacked patterns can still shimmer. The character currently uses nearest texture filtering while room surfaces use linear mipmaps, so its edge treatment is also different before the overlay.

## Smallest recommended implementation

1. **Keep one gallery finish, reusing `_post()`.** Fetch native texels with `texelFetch`, clamp coordinates at edges, apply current RGB6 arithmetic to each fetched sample, then a vertical filter, then bilinear reconstruction. Four vertically filtered corner values share eight unique samples (two columns × four rows), so this needs neither another viewport nor a plugin. Keep sampler/color-space conventions consistent with the current Compatibility canvas route; do not add a second manual sRGB conversion by assumption. Godot exposes integer texel fetch and explicit sampler filtering. [Godot shader language](https://docs.godotengine.org/en/stable/tutorials/shaders/shader_reference/shading_language.html)
2. **Start with a controlled softening comparison.** **T:** compare no vertical copy filter against ¼–½–¼. At the current roughly 320-high internal render, the full 480-line kernel may look excessively soft; a 50% blend gives ⅛–¾–⅛ as an explicitly artistic approximation. Keep the source grid fixed during each run, leave aspect/camera untouched, and record actual `_vp.size`. Change resolution only if this comparison demonstrates a need. Do not simulate alternating fields or clamp game motion to 30 fps based on the upload.
3. **Stop stacking textures over the gallery.** **T:** use existing quiet-rectangle plumbing to bypass the CRT's mask/grain/scanline and channel separation for this area, and attenuate/bypass the outer haze there. Preserve the shell elsewhere. If preserving shell curvature, use the same warped coordinate for the exclusion rectangle so mouse mapping stays consistent. A haze exclusion operates in final-screen coordinates, which must account for shell curvature; do not blindly reuse an unwarped rectangle at its edges. No new LUT, noise texture, glow, normal-map pass or real-time lights.
4. **Use the white navigation rooms as checks.** White remains white, a warm off-white patch retains its hue, black stays black, silhouettes stay visible against white, and a gradient does not acquire a large checker. Walk through both doorways, stop, reverse, turn the head, and inspect art detail. Capture fixed-position idle frames and moving video in the actual exported Compatibility renderer. Existing benchmark should remain near the established 60 fps on the tested Chrome machine; shader tap count alone is not performance evidence.
5. **Ask blind reviewers to separate material, light and display.** Same camera/bake/character for the shader A/B; same shader for character A/B. Compare actual-size images plus 2× crops, then motion. A still can judge softness and white preservation but cannot certify crawl, footstep synchronization or animation seams.

Godot's screen-reading mechanism has copy-order constraints; overlapping `hint_screen_texture` effects do not automatically form an unlimited sequential chain. This is another reason to prefer explicit viewport-texture sampling inside the current gallery pass rather than adding several screen-overlay nodes. [Godot screen-reading shaders](https://docs.godotengine.org/en/stable/tutorials/shaders/screen-reading_shaders.html)

## What the overlay cannot repair

It cannot create side-facing character poses, articulated hands/head, correct contact frames, correct room-entry movement, believable spatial lamp pools or the missing appearance of a mesh face. A vignette would darken paintings and character with the same screen-space rule, irrespective of their world position. Bloom cannot substitute for light arriving on the wall; blur cannot substitute for a clean silhouette. The owner's 57:32 scene is useful because room lighting, contact shade, material pattern and display softness remain separable.

**Recommended review target:** clean GameCube-like softened output with subtle native-scale quantization, stable movement, preserved whites, warm baked pools and readable characters. This is a testable visual approximation. Exact original console/capture reproduction is neither established from these frames nor desirable where it would reproduce visible interlace/tearing artifacts.

## Implemented prototype trial under #135

After the research, the coordinator authorized the minimum runtime trial. [`gamecube.gdshader`](../../modules/shell/prototype/gallery_walk4/gamecube.gdshader) implements the eight-fetch reconstruction above, with `copy_filter=0.5`. Shell CRT/haze now bypass their finish inside the gallery's existing quiet rectangle; shell curvature and its matching input transform remain. The rectangle has an explicit nonempty-size guard so the sentinel `Vector4.ZERO` cannot accidentally exempt pixel (0,0). The haze uses the same curve/aspect/scale mapping, including CRT-disabled mode. Outside the gallery the existing effect arithmetic is unchanged. Wiring the new shader into `walk4.gd` is the coordinator's task; this report's author did not edit that shared file.

Two actual GPU checks passed on Godot 4.7.2 Compatibility/OpenGLES3.1, Microsoft D3D12 RTX4070SUPER:

- [Quantizer check](../../modules/shell/prototype/gallery_walk4/final_render_check.gd): 1,600 pixels at each filter strength 0, 0.5 and 1 compared with a CPU reference of quantization, clamped-edge taps and interpolation. Maximum channel errors 0.002466, 0.002615 and 0.002484, all below one 8-bit output code (1/255). Exact white/black preservation also passed. [Output](gallery-final-render-overlay/gpu-quantizer-check.log)
- [Quiet-stack check](../../modules/shell/prototype/gallery_walk4/final_render_check.gd): CRT and haze combined preserve all 1,600 source pixels inside the exclusion region, maximum error 0. Outside the region their effect remains observable (red-channel change 0.117647 at the check pixel). [Output](gallery-final-render-overlay/gpu-quiet-check.log)

Run from the worktree with `source /home/reidsurmeier/promo-lab/gpu-env.sh`, then `godot --rendering-method gl_compatibility --path . --script modules/shell/prototype/gallery_walk4/final_render_check.gd`. These tests verify shader arithmetic, compilation and exclusion. They do **not** certify the final viewer's appearance, curved exclusion edges in a resized browser, motion stability or exported browser speed. Those remain required integrated checks.
