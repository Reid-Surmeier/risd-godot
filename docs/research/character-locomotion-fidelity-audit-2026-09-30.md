# Why the live character does not yet feel like GameCube Animal Crossing

Research for [prototype issue 231](https://github.com/Reid-Surmeier/risd-godot/issues/231), 2026-09-30. The owner rejected the live demo's speed and overall animation fidelity. This audit follows public decompiled controller, actor, animation, renderer, and effect code end to end. It is a research diagnosis, not an acceptance verdict or an exact reconstruction claim. No paid calls, ROM, original mesh download, new dependency, or runtime module change was used.

## The practical finding

The current character has three independent problems: its movement controller selects the wrong gait for full keyboard input; the retargeted body's proportions and articulation differ from the source; and its comparison evidence omits the transitions and interactions a player notices while moving. Increasing movement speed alone addresses the owner's immediate complaint but cannot fix those other problems. The old controller moves at a fixed 1.05 target units/second, or 1.8 with Shift, regardless of animation phase, with a fixed 0.8-second WALK clip and 0.467-second DASH clip. Those settings were prototype choices, not numbers recovered from Animal Crossing. Local evidence: [audited controller](../../image-work/character-pilot/live-demo/demo.gd), [earlier source and footage note](character-video-reference-2026-09-30.md).

The strongest new evidence is that the game treats movement speed, turning, phase speed, and gait selection as a coupled system. WALK, RUN, and DASH all use the same movement calculation. They differ in pose, state thresholds, and effects. A full keyboard press should therefore not be identified with the game's gentle partial-stick WALK just because the button says “walk.” [Shared movement route](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player_main_run.c_inc#L42-L59), [DASH delegation](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player_main_dash.c_inc#L38-L40), [controller magnitude](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player_controller.c_inc#L139-L156).

## What is verified, and what remains uncertain

All source citations are pinned to ACReTeam/ac-decomp commit `09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c`. This is a community decompilation of the game, not Nintendo's released source code. Its implementation is stronger evidence than a generic animation tutorial, but version branches, matching status, hardware math, and the reference video's actual executable still matter. The repository license does not clear the original game's artwork. [Repository](https://github.com/ACreTeam/ac-decomp/tree/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c), [version-dependent keyframe implementation](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/c_keyframe.c#L428-L548), [license](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/LICENSE).

The normal update model is supported by a complete call route: initialization selects `GAME_FRAME=1`; that is passed to the display's frame-rate setting; the display waits on video retrace messages; its initial render mode is NTSC; active play calls the actor traversal once; that traversal calls each eligible actor's movement procedure once. This supports a normal approximately 60-update/second NTSC model. It does not prove 60 updates for the European trailer, PAL releases, altered emulator speed, dropped capture frames, paused menus, or every revision. Results below always state where 60 updates/second is assumed. [Game initialization](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game.c#L210-L215), [GAME_FRAME](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/include/game.h#L37), [display rate](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game.c#L115-L128), [retrace wait](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/static/JSystem/JFramework/JFWDisplay.cpp#L314-L333), [NTSC mode](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/static/JSystem/JFramework/JFWSystem.cpp#L28), [play traversal](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_play.c#L523-L539), [actor call](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_actor.c#L457-L476).

There are **three different “half” quantities** that must not be mixed together. Actor displacement is half its velocity each update. Morph counters change by 0.5 each update. Animation phase advances by the full `frame_control.speed` each update, without a second half multiplier. The player's combined animation route calls each frame controller once after evaluating/combining the layers. [Actor displacement](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_actor.c#L43-L62), [phase update](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/c_keyframe.c#L157-L175), [actual player combine/play route](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/c_keyframe.c#L1017-L1075).

## Speed and cadence: the old controller is using the wrong reference state

The original controller computes an analog magnitude from stick X/Y, applies a dead zone, clamps its radius, and stores both movement and corrected recognition percentages. The raw movement radius is what locomotion reads. The header gives raw thresholds 9.899495 and 61, so digital keyboard input is a different input distribution from someone gently tilting a GameCube stick. Dash input is accepted from **B, L, or R**, not solely B. [Stick processing](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_controller.c#L26-L65), [thresholds](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/include/m_controller.h#L34-L37), [dash buttons](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player_lib.c#L3706-L3708).

On flat ground, aligned to the desired heading, the movement target is `4.875 * stick_magnitude` without a dash button, or `7.5 * stick_magnitude` with one. Actor speed increases by 0.60899997 per update and decreases by 0.32625002, clamped to the target. Those are source velocity increments per update; they are not meters/second or ready-to-copy Godot accelerations. Source translation uses half of actor speed per update, along actor heading. [Target speed and acceleration](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player_main_walk.c_inc#L156-L194), [actor velocity and movement](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_actor.c#L43-L62).

The movement-to-animation coupling is approximately:

```text
phase_step = max(0.22, 0.59999996 * sqrt(actor_speed * slope_normalizer / 7.5))
full_cycle_updates = 16 / phase_step
full_cycle_seconds = full_cycle_updates / update_rate
```

Wall collision modifies this expression before the low-speed clamp; two walls have a special case. A one-wall collision multiplies the phase step by the square root of the sine magnitude between the wall and actor heading. This is animation feedback about constrained movement, absent from the prototype. Source `Math3DVecLengthSquare` is used in the uphill normalizer; preserve the code's operation rather than casually replacing it with a length. [Phase and wall response](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player_main_walk.c_inc#L78-L105), [uphill normalizer](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player_common.c_inc#L2131-L2158).

Calculated steady flat-ground results, assuming 60 updates/second:

| Source velocity parameter | Phase step/update | Full-cycle duration | Source world displacement/cycle |
| --- | ---: | ---: | ---: |
| WALK-to-RUN threshold 3.525 | 0.41134 | 0.64829 s | 68.557 world units |
| Ordinary full stick 4.875 | 0.48374 | 0.55127 s | 80.623 world units |
| Full stick plus dash button 7.5 | 0.60000 | 0.44444 s | 100.000 world units |

The source clips end at frame 17 with a start at 1, hence 16 phase intervals, not 17 evenly spaced poses. WALK requests RUN when the squared phase step divided by .048 reaches 3.525; RUN requests WALK below 3.525 or DASH at/above 4.875; DASH requests RUN below 4.875. A partial-stick movement spans several speeds and gaits. [Authored clips](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/data/model/player_anim.c#L43), [WALK transition](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player_main_walk.c_inc#L258-L268), [RUN transitions](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player_main_run.c_inc#L95-L103), [DASH fallback](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player_main_dash.c_inc#L178-L186).

**Floating-point caveat:** real-valued algebra puts ordinary full-stick exactly on the RUN-to-DASH threshold. A binary32 reconstruction with `.59999996f` instead gives a phase step of 0.48373544216156006 and reconstructed gate 4.874999523162842, just below 4.875. Thus it is wrong to assert that ordinary full stick definitively enters DASH. RUN at approximately 0.551 s is the safer normal full-stick candidate; DASH at approximately 0.444 s is the held-button candidate. This is a mathematical reproduction, not a console state trace; compiler/platform details and wall/slope changes can affect the equality. [Gate implementation](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player_main_run.c_inc#L95-L103).

On a straight, already aligned start with no slope or collision, the velocity calculation alone takes **9 updates** to reach 4.875 and **13 updates** to reach 7.5; releasing full normal input takes **15 updates** to reach zero, or **23** from full dash. At 60 updates these are approximately .150/.217 seconds accelerating and .250/.383 seconds braking. They are not end-to-end input latency: WAIT initially requests WALK, subsequent state requests settle separately, and turning changes the target. This distinction is testable by recording the speed parameter, applied world displacement, animation state, and phase on every update. [Acceleration/deceleration](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player_main_walk.c_inc#L180-L194), [WAIT request](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player_main_wait.c_inc#L97-L99).

## World scale is unresolved: do not turn source units into invented meters

The player actor explicitly has scale .01 on all axes. The renderer loads world translation and shape rotation, then multiplies by actor scale before drawing the skeleton. A source thigh of 450 and shin of 400 therefore occupy 8.5 source world units combined, while our generated skeleton's measured corresponding chain is 0.399101749 target asset units. Matching leg length alone gives `target_units/source_world_unit = .399101749/8.5 ≈ .046953`. Under the 60-update model that maps ordinary full stick to approximately **6.867 target units/second**, and held dash to **10.564**. This is an inferred skeleton-based scale, **not an accepted speed or a meter conversion**. [Player scale](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player.c#L511-L513), [actor render transform](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_actor.c#L252-L259), [source leg offsets](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/data/model/boy_model.c#L396-L406), [target measurement](character-video-reference/proportion-analysis.json).

That inference reveals a problem rather than resolving it: ordinary source translation is 80.623 source world units per cycle, or **9.485 source leg lengths**, independent of update-rate assumptions. Matching target leg length gives approximately 3.785 target units per cycle. Our source DASH reconstruction's shoe-joint forward/back span is only about 15 source world units. This cannot be silently called a planted, no-slip stride. The shader/mesh sole, time actually spent in stance, actor lean, and capture displacement have not been recovered here. Motion airborne between brief contact events also differs from a long stationary stance. Nothing in the examined locomotion route enforces a world-space foot anchor; that does **not** establish that the designers intentionally wanted visible sliding. A slower modern controller with planted IK could be an intentional adaptation, but is not automatically a more exact recreation. [Source actor movement](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_actor.c#L43-L62), [source locomotion route](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player_main_dash.c_inc#L201-L214), [reconstruction and its limits](character-video-reference-2026-09-30.md).

Before declaring a speed matched, measure character travel relative to stable ground features or camera-corrected map geometry, normalize by the same visible body landmark span, and compare the original and candidate's distance per full cycle. Camera scroll makes screen-center character position useless for this task. Neither changing the speed to 6.867 nor retaining the old 1.05 proves correctness. The owner-requested faster demo can be a clearly labeled usability calibration while that measurement remains open. This is a proposed comparison procedure, not an observed source result.

## Turning, start/stop, and blending explain many “small interactions”

Original movement turns the actor toward the camera-relative input angle using a magnitude-dependent factor, bounded to **2500 binary-angle units ≈13.733° per update**, with a **50-unit ≈0.275° minimum**. Full-stick interpolation factor is `1-sqrt(.5) ≈.292893`; weaker input uses a smaller factor. The angle helper applies wrapping, integer truncation, min/max steps, and overshoot correction. Crucially, desired speed is then multiplied by `max(cos(input_angle-actor_heading),0)` and movement follows actor heading. A reversal initially slows the character instead of sliding it sideways while the mesh catches up. The old demo instantly moves in the new input direction and only rotates the model afterward; changing `lerp_angle` alone does not fix that mismatch. [Turn and heading-speed coupling](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player_main_walk.c_inc#L131-L194), [angle helper](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_lib.c#L554-L593), [camera-relative input](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player_common.c_inc#L2254-L2258).

DASH has a separate turn/skid request when its source controller difference reaches **18204 binary-angle units ≈100°**. The difference helper uses its own controller-angle convention; do not assume it is interchangeable with the camera-relative movement angle in every scene. `TURN_DASH` selects **RUN_SLIP1**, creates a turn effect and slip sound, brakes by .261 per update, and rotates its **shape** toward the requested direction using `add_calc_short_angle3`. That second helper advances through positive wrapped angular space; it is not the ordinary shortest-angle helper. On settling it writes a right-foot turn footprint and synchronizes world heading to shape heading. This explicit state is absent from the live demo. [Trigger and fallback](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player_main_dash.c_inc#L178-L186), [difference helper](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player_common.c_inc#L2261-L2268), [skid setup/movement/settle](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player_main_turn_dash.c_inc#L17-L76), [directed turn helper](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_lib.c#L611-L640).

Idle/start/stop also has phase semantics. WAIT requests WALK with flag 4, causing a frame-1 start. WALK/RUN/DASH changes normally reuse the old animation frame. Releasing the stick keeps the locomotion state until speed reaches zero, using the deceleration above; ordinary WAIT itself uses braking .23925. WALK settling can emit an additional footstep depending on the outgoing phase. The old demo enters Idle immediately from input release and resets clips on state change, so its pose transition can be smooth-looking while its contact timing is wrong. [WAIT startup](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player_main_wait.c_inc#L97-L99), [WALK starting frame and settle](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player_main_walk.c_inc#L40-L73), [RUN frame preservation](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player_main_run.c_inc#L16-L29), [DASH frame preservation](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player_main_dash.c_inc#L16-L29), [stop gate](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player_main_walk.c_inc#L264-L269), [WAIT braking](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player_main_wait.c_inc#L58-L60).

Most ordinary state changes request morph counter -5. A negative morph counter evaluates the new moving pose, blends current toward target with step `.5/abs(counter)`, advances the clip, and moves the counter toward zero by .5 per update: **10 updates ≈.167 s** under the 60-update model. This is a joint-space, quantized blend against an advancing target, not proof that a generic .15-second quaternion crossfade is identical. Positive morph counters pause phase advancement while blending. The old .15-second demo fade is close in duration but does not preserve original phase or interpolation rules. [Morph requests](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player_main_run.c_inc#L97-L103), [morph coefficient](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/c_keyframe.c#L367-L385), [actual player layer/morph update](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/c_keyframe.c#L1057-L1075).

The original also adds whole-actor forward lean derived from phase speed. Algebraically it is `min(20°,20°*(phase_speed²/.36)^6)`, eased with the same approximately .292893 factor and a 10°/update cap, then recovered toward zero in WAIT and TURN_DASH. Ordinary full stick gives about **1.508°**, full dash **20°** before easing. Retargeting only local bones omits that actor transform; speeding up the clip without this change misses a very visible sprint silhouette. [Lean](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player_common.c_inc#L2165-L2184), [state calls](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player_main_dash.c_inc#L205-L214), [WAIT recovery](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player_main_wait.c_inc#L104-L114).

## Rig fidelity: the current metrics prove repairs, not resemblance

The original boy skeleton has 26 joints with segmented display lists and vertex batches assigned to matrices; individual display lists can switch matrices internally, so a whole named part is not necessarily rigid to one joint. The renderer traverses the hierarchy, applies each joint transform, and draws the associated display list. The source count includes tail/emotion anchors; a difference of 26 versus 24 alone does not establish a missing functional motion. The generated character is a smooth weighted 24-bone mesh with a different hip width, arm length, shoulder width, foot volume, and additional helper joints. A matching global quaternion on one mapped bone therefore does not produce matching silhouettes, joints, or shoe contact. [Source hierarchy](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/data/model/boy_model.c#L396-L425), [part renderer](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/c_keyframe.c#L724-L805), [internal matrix-assigned head batches](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/data/model/boy_model.c#L38-L85), [measured proportion mismatch](character-video-reference/proportion-analysis.json).

The measured source arm/leg ratio is **1.47176**, versus the generated skeleton's **1.02132**. Source hip/shoulder width ratio is **.77778**, versus target **.41449**. These are rest-joint measurements, not guaranteed visible dimensions. Uniform scaling cannot make both equal; rotation fixes cannot make the generated boots have the source's sole or pivot. Our reduced arm compression and rigid-head seam repair are useful deformation checks, but they do not certify original-game anatomy or motion. [Earlier measurements and interpretation](character-video-reference-2026-09-30.md), [arm repair audit](character-arm-weight-refinement-2026-09-30.md), [derived motion comparison](character-video-matched-iterations.md).

There is a further identity mismatch: the supplied screenshot appears to show the character **carrying a tool**, while the bare-handed motion references and prototype do not represent that tool state. The source has two animation layers selected **per joint** by a part table. Axe overlays select both arm chains and the hand; net/pickup overlays select the right arm and hand. Locomotion setup selects item animations, including a special moving-rod route, and draw callbacks retain actual hand matrices for attached items. A screenshot-to-mesh generation cannot recover that behavioral layer from clothing texture. The exact held tool in the supplied low-resolution screenshot remains unverified here; do not label it an axe as a fact. [Part tables](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/data/player/BOY_part_data.c#L43-L132), [moving-item selection](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player_common.c_inc#L3936-L3951), [hand/item matrix callbacks](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player_draw.c_inc#L80-L97), [right-hand matrix](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player_draw.c_inc#L128-L137).

Head geometry should stay rigid, but the source head is not frozen in world orientation. Its parent is animated, and a prerender callback composes extra head X/Y angles onto the authored rotation. This pass verified the callback but did not establish every writer of `head_angle`, so automatic gaze tracking during ordinary walking remains unverified. It would be another error to invent camera-tracking eyes and call them original. The combined keyframe route can additionally apply a per-joint rotation-difference table before morph/phase advancement; the current decoded reference explicitly omits it. This pass verified that conditional mechanism, not that a nonzero correction is active during a specific gameplay clip. Log or reconstruct the actual correction values before attributing head/shoulder discrepancies to those corrections. [Joint correction application](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/c_keyframe.c#L1041-L1055).

The original also cycles eye textures with a blink pattern and random timers; our texture is static. A blink/face atlas is separate from head skinning, and a future interaction comparison should include it. [Head callback](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player_draw.c_inc#L1-L15), [blink texture scheduling](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player_common.c_inc#L900-L931), [eye and mouth texture selection](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player_draw.c_inc#L184-L228).

## Effects and contact feedback are state- and surface-specific

Source locomotion emits foot effects when phase crosses frames **1/9**, using separately recorded left/right foot positions and angles. WALK/RUN effects differ from DASH effects. The callbacks associate joint 5 with the left foot and joint 9 with the right foot. These labels do not repair the generated model's reversed lower sole in the WALK trial; source events and target geometric contact must both be inspected. Ordinary grass WALK/RUN has no generic dust; bush/season cases can emit leaves or snow. DASH chooses dust on ordinary dry ground, no dust on interior floor, sand splashes on sand, water splashes in water/rain, and snow or leaves in their own surface/season combinations. DASH also has flower-trampling logic. The current five white spheres at every DASH event approximate only one dry-ground situation. A “good dust loop” is insufficient evidence for effects fidelity across the demo's visible path, grass, walls, and trees. [WALK effect](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/effect/ef_walk_asimoto.c), [DASH weather/surface dispatch](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/effect/ef_dash_asimoto.c#L43-L155), [flower interaction](https://github.com/ACreTeam/ac-decomp/blob/09ca8e8b5b24e6ab44047ee980cf0088ad7ecb4c/src/game/m_player_main_dash.c_inc#L42-L70).

Original dry DASH dust uses an authored textured effect, white color for argument 8, an initial backward local velocity -2 and upward velocity +1, acceleration `(0,-.05,.075)`, timer 18, and a texture/alpha schedule. The generic effect actor moves it once and decrements the timer each update, implying approximately **.30 s** at 60 updates/second, not the prototype's .24-second linearly shrinking spheres. The renderer uses its effect transform helper and animated texture slots. Do not equate a sphere's radius to the source .01 scale without knowing that effect model's dimensions. Sound feedback also selects indoor floor/surface/bridge cues and contributes to perceived contact. ## Comparison procedure that can catch the remaining defects

The existing 0.8-second YouTube crops contain changes in yaw, a wide-capture aspect mismatch, low-resolution shoe pixels, and no recovered stick magnitude or state. They helped locate cadence and gross deformation but cannot establish exact rig or locomotion matching. The Nintendo trailer and uploader footage are complementary observations, not controller-input ground truth. [Existing footage provenance and measured uncertainty](character-video-reference-2026-09-30.md), [Nintendo GameCube page](https://www.nintendo.com/en-gb/Games/Nintendo-GameCube/Animal-Crossing-267719.html), [Mutch Games outdoor reference](https://www.youtube.com/watch?v=EwwW4Rk1wMU&t=1015s).

Five bounded next tests would answer the largest remaining questions without another image/3D generation batch:

1. **Steady movement:** compare normal full input and held dash separately, at front, side, and rear yaw. Fit camera/aspect and visible body scale first; measure floor-relative travel and full-cycle cadence independently. Keep RUN1 as a real candidate rather than stretching WALK1 to masquerade as running.
2. **Start and stop:** show Idle→WALK→RUN and release-to-stop at each quarter-cycle. Track velocity, phase, outgoing sole position, actor lean, and event times through the whole transition. A still floor-minimum check cannot detect sliding or phase resets.
3. **Direction changes:** repeat 45°, 90°, and 180° input changes at normal and dash speed. Show actor heading separately from velocity direction, and record whether a distinct skid state matches the reference. Compare original input-angle conventions rather than dropping in one generic lerp.
4. **Rig and carried item:** include ordinary moving gaze, a visible look interaction, and relevant tool-held walking; compare projected landmark trajectories and silhouette dimensions of head, shoulders, wrists, knees, and shoes under the same view, with occluded landmarks omitted. Review unarmed and relevant tool-layer poses independently; settle generated proportions before claiming retargeting accuracy.
5. **Ground and feedback:** compare ordinary grass, dry path, indoor floor, and one edge/collision case. Push into the same wall and then slide along it: record commanded speed, measured actual displacement, heading, phase rate, and dust births. This can falsify the current input-driven animation when the body is blocked. Verify contact position, sound, dust type, lifetime, and stop suppression. Assess world-foot drift over each actual stance interval; source-effect timing is not a stance detector.

Success means the owner can inspect these interactions and agree that they resemble the chosen GameCube reference, with measured mismatch and uncertainty disclosed. It does not mean a submillimeter generated-mesh floor check passed. The next minimal implementation should add the missing **RUN1** candidate and speed-driven gait selection, correct gait/speed coupling and heading-dependent movement, then preserve transition phase and evaluate rig proportions and skid/effects in those fixed scenarios. A preference-based speed increase can be published sooner as a provisional change; it does not settle RUN selection or source fidelity. More procedural layers or more mesh generations before those tests would obscure the diagnosis.

This pass downloaded only pinned public C/header files into `/tmp/character-fidelity-source`, under 2 MB before the local derived DASH transform JSON. This did not execute a game binary or include the original mesh, actor yaw/lean, prerender callbacks, or hardware lookup math.

The binary32 threshold caution is reproducible using the Python standard library:

```python
import math, struct
f32 = lambda x: struct.unpack('f', struct.pack('f', x))[0]
step = f32(f32(.59999996) * f32(math.sqrt(f32(f32(4.875) / f32(7.5)))))
gate = f32(f32(step * step) / f32(.048))
assert gate < f32(4.875), (step, gate)
```

Calculated timing and displacement are formulas evaluated from source, not captured runtime metrics. The legacy live controller values above describe the rejected version audited at the start of this research; subsequent demo tuning should be reported separately. Original-game contact geometry, matching release/revision, input trace, full projected-body registration, and accepted world-speed scale remain open.
