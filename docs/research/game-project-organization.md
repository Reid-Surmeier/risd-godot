# Game project organization and asset retention

Checked 2026-09-27 against official Godot, Git and Git LFS documentation. Applied observations refer to `8b26833a` in the current `build-integrated` checkout. This report proposes changes; it does not move, delete or migrate files.

## Findings

| Concern | Official guidance | Application here |
| --- | --- | --- |
| Runtime structure | Godot suggests keeping assets near the scenes that use them; third-party runtime extensions generally belong in `addons/`, while character art can remain with its character. [Project organization](https://docs.godotengine.org/en/stable/tutorials/best_practices/project_organization.html) | Keep the existing `modules/<name>/` organization and frozen module interfaces. Put accepted runtime art and provenance with its consumer; do not introduce an additional generic `src/` hierarchy merely for neatness. |
| Import metadata versus cache | Source-side `<asset>.import` files contain configuration and should be committed. `.godot/imported/` is regenerated from originals and settings. [Import process](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/import_process.html) | `.gitignore` currently ignores **all `*.import`**. Audit existing intentional settings, then preserve runtime import metadata; deleting caches before doing so risks losing per-asset choices. Do not confuse source settings with imported texture payloads. |
| Research and experiments | An empty `.gdignore` prevents importing an entire directory; ignored resources cannot be loaded through `load()`/`preload()`. [Project organization](https://docs.godotengine.org/en/stable/tutorials/best_practices/project_organization.html) | Use this for proven non-runtime research, evidence and reference-source folders. Check actual references first: `prototypes/painting-coverflow/web/` supplies live paintings and JSON, and `modules/shell/prototype/gallery_walk4/` is the retained live gallery. Blanket-ignoring every folder named “prototype” would break the current build. |
| Export selection | Godot supports exporting chosen scenes/resources with dependencies, plus inclusion filters for non-resource files. `export_presets.cfg` is versionable; credentials live separately. [Exporting projects](https://docs.godotengine.org/en/stable/tutorials/export/exporting_projects.html) | Keep boot and game pack roles explicit. Audit the current `all_resources` game preset and exclusions against a pack listing. JSON and dynamically loaded assets need explicit coverage; do not switch blindly to scene-only export. Web video and Flowers sidecars remain part of the distributable even when absent from the PCK. |
| Git ignores | Ignore patterns affect untracked files, not files already committed. [gitignore](https://git-scm.com/docs/gitignore) | Adding `__pycache__/`, export or evidence rules will not remove historic blobs or stop already-tracked artifacts appearing in checkouts. Classification, untracking and history cleanup are separate operations. |
| Large accepted binaries | Git LFS stores small Git pointers and separate large-file objects; tracking rules must be committed. Existing history migration is a separate operation. [Git LFS](https://git-lfs.com/), [migration manual](https://github.com/git-lfs/git-lfs/blob/main/docs/man/git-lfs-migrate.adoc) | Consider LFS for selected retained GLBs, large source media and changing binary masters after verifying remote storage and CI checkout support. Do not put every PNG into LFS by habit. LFS is not a low-disk emergency fix: working files still occupy space and migration can rewrite commits. |
| Worktrees | Linked worktrees share repository data while retaining separate working directories and per-worktree state. Git provides listing, removal and stale-record pruning. [git-worktree](https://git-scm.com/docs/git-worktree) | Keep the existing canonical build checkout documented in `docs/project-home.md`. Branch history does not preserve ignored originals. Remove only explicitly approved, verified inactive worktrees; pruning administrative records is not a substitute for content-preserving cleanup. |

## Smallest useful arrangement

Retain the existing folders and clarify ownership before moving anything:

- **Game:** `project.godot`, `modules/`, selected shared `assets/`, runtime web shell, export presets and required sidecars. Keep implementation, tests and accepted assets together under the established modules.
- **Authoring and originals:** `image-work/` for small recipes/provenance and intentional selected inputs; preserve large generated originals, rejected candidates and museum media in the existing hashed external archive. A paid generated original is not reproducible merely because its prompt survives.
- **Knowledge and proof:** `docs/research/` for findings, `docs/adr/` for decisions, `docs/evidence/` for a small decisive set tied to commit IDs. Keep long recordings and exhaustive run dumps in the preserved external evidence store with hashes and retrieval locations.
- **Dependencies:** keep package manifest/lockfile as runtime authority. `repos/` is explicitly read-only source reference, not a runtime import source; its existing manifest records exact upstream refs. Preserve licenses and provenance. Do not replace this repository's required vendoring policy with a new dependency system during organization work.
- **Rebuildable output:** `build/`, `.godot/`, `node_modules/` and ordinary run caches remain disposable only after confirming no unique originals or import decisions are mixed in. The existing export script is the build entry point; avoid another parallel export folder convention.

Recommended first scoped change: inventory runtime references and import metadata, add Godot-ignore markers only to confirmed non-runtime folders, and verify a clean import/export plus current Sketchbook/gallery interactions. Compare exported pack contents and bytes before claiming a saving. Defer physical folder relocation and LFS history migration until their concrete benefit, rollback and approved scope are clear. `docs/project-home.md` already provides the appropriate single owner-facing index; extend it instead of creating competing project-home guides.
